# StoryCaldron 设计文档

> 目的：让后续开发与维护人员在不通读全部源码的情况下，也能理解系统结构、数据流向与关键约定。
> 最后更新：2026-10-13（与 `collab_novel_agent.py` / `project.py` / `web_server.py` 当前实现保持一致）。

## 1. 系统定位

StoryCaldron 是一个「多 Agent 协作小说创作」系统：用一张 LangGraph 工作流，把一章小说的
创作拆成「规划 → 写草稿 → 连续性检查 → 文风润色 → 人工审核 → 记忆更新 → 正典提案 → 落盘」
等节点，每个节点由大模型驱动，并支持在「人工审核」处暂停、由人介入修改或采纳。

整体分三层：

```
┌──────────────────────────────────────────────────────────────┐
│  前端（web/，Vue3 + Vite）  · 工作台 UI                       │
│  - 项目/素材卡/章节管理、写作看板、Agent 流式输出、人工审核面板 │
└───────────────┬──────────────────────────────────────────────┘
                │ HTTP / JSON  （BaseHTTPRequestHandler，单端口）
┌───────────────▼──────────────────────────────────────────────┐
│  后端服务（backend/web_server.py）  · 薄 HTTP 层              │
│  - 项目/卡片/章节 CRUD、Markdown 导入、写作会话控制、静态托管  │
└───────────────┬──────────────────────────────────────────────┘
                │ 直接调用
┌───────────────▼──────────────────────────────────────────────┐
│  核心逻辑（backend/collab_novel_agent.py + project.py）        │
│  - collab_novel_agent：LangGraph 工作流、LLM 调用、写作编排    │
│  - project：项目/卡片/章节 的本地文件存储（JSON + txt）       │
└──────────────────────────────────────────────────────────────┘
```

## 2. 目录与模块职责

| 路径 | 职责 |
|------|------|
| `backend/collab_novel_agent.py` | 创作核心：状态定义、LangGraph 构建、各节点函数、`_call_llm` 单一 LLM 入口、`start_session`/`run_session`/`submit_human_action` 等对外 API。 |
| `backend/project.py` | 项目存储层：项目目录初始化、卡片读写、章节落盘、project.json 元信息。纯文件操作，不依赖 LLM。 |
| `backend/web_server.py` | HTTP 层：路由分发、请求解析、把前端请求转成对 `project` / `collab_novel_agent` 的调用；并托管 `web/dist` 静态产物。 |
| `backend/data/` | 演示模式（无项目目录）下的全局素材卡与章节输出目录。 |
| `backend/output/` | 演示模式章节输出目录。 |
| `backend/projects/` | 多项目根目录，每个子目录是一个项目工作区。 |
| `backend/md_to_cards.py` | Markdown→卡片转换工具（命令行/导入接口复用），可接 LLM。 |
| `web/src/` | 前端源码：`App.vue` 外壳、`store.js` 全局状态、`api.js` 接口封装、`components/*` 各面板。 |

## 3. 数据模型（项目工作区）

一个项目 = `<root>/` 目录，内部结构：

```
<root>/
  project.json            # 项目元信息：title、setting 摘要、chapters 章节索引
  cards/                  # 素材卡（每类一个 JSON 文件，键为 id）
    characters.json       # 人物卡
    stories.json          # 剧情卡（兼容旧名 plots.json）
    styles.json           # 文风卡
    foreshadowing.json    # 伏笔卡
    wordviews.json        # 世界观卡（文件名拼写如此，非 worlds）
  chapters/               # 章节正文 chapter_001.txt ...（并按顺序命名）
```

**卡片类型约定**（`project.CARD_TYPES`）：

| type | 文件 | 中文标签 |
|------|------|----------|
| character | characters.json | 人物卡 |
| plot | stories.json（无则 plots.json） | 剧情卡 |
| style | styles.json | 文风卡 |
| foreshadowing | foreshadowing.json | 伏笔卡 |
| worldview | wordviews.json | 世界观卡 |

- 卡片以 `id` 为主键，整文件按 id 覆写（`create_card` / `save_cards`）。
- `load_cards` 只在 `project/cards/` 内读取（**已修复**：不再回退到全局 `data/`）。
- 演示模式（前端不传 `project`）才用全局 `DATA_DIR` / `OUTPUT_DIR`。

## 4. 创作工作流（LangGraph）

图在 `collab_novel_agent.py` 末尾 `graph.compile(checkpointer=MemorySaver(),
interrupt_before=["human_review"])` 处构建。节点与边：

```
START → load_context → plan_chapter → approve_card
approve_card --approved--> write_draft
approve_card --rejected--> plan_chapter        (带重试上限，超限强制通过)
write_draft → check_continuity
check_continuity --clean--> style_edit
check_continuity --issues_found--> fix_issues → check_continuity   (循环修正)
style_edit → human_review  ★interrupt_before 在此暂停
human_review --approved--> update_memory
human_review --revise--> style_edit           (回到润色，可多次)
update_memory → propose_canon → approve_canon
approve_canon --approved--> commit → END
approve_canon --rejected--> update_memory      (带重试上限，超限强制通过)
commit → 把 final_chapter 写入 <project>/chapters/ 并更新 project.json
```

**关键设计点：**
- 状态对象 `CollabNovelState` 是单个大字典，贯穿所有节点（见 `start_session` 初始字段）。
- `track_step` 装饰器负责把每个节点的进展打印/记录到 `step_logs`，供前端「写作看板」轮询展示。
- `human_review` 节点本身不干活，真正暂停靠 `interrupt_before`，由前端 `api_write/action`
  提交 `approved` / `revise` / `edit` / `quit` 后再 `app.invoke` 续跑。
- `approve_card` 与 `approve_canon` 的「驳回→重做」有重试计数上限，避免无限循环（超过上限强制通过）。

## 5. LLM 调用约定

- 唯一入口：`_call_llm(prompt, system, temperature)`，失败返回 `""` 供上层降级。
- 客户端工厂 `get_llm(temperature)` 按温度缓存 `ChatOpenAI` 实例，不同角色（规划/草稿/润色…）温度不同。
- 默认指向**本地 llama.cpp**：`http://localhost:8080/v1`，key=`dummy`（见 `DEFAULT_LLM_*`）。
- 可用环境变量覆盖：`LLM_MODEL` / `LLM_BASE_URL` / `LLM_API_KEY`。
- 因本地服务连接复用偶发 404，默认 `LLM_FORCE_CONNECTION_CLOSE=True`（每次新建连接）。

> 注意：当前默认不是 DeepSeek/云端，必须在 `localhost:8080` 起了兼容 OpenAI 的推理服务才能跑通写作；
> 接云端需设置上述环境变量（详见《开发指南》）。

## 6. 后端 HTTP 接口契约

基底：`http://127.0.0.1:8765`。所有接口 `application/json; charset=utf-8`。
`project` 参数传项目绝对路径；省略则走演示模式（`projects/default` 或全局 `data/`）。

### GET
| 路径 | 说明 | 返回 |
|------|------|------|
| `/api/health` | 健康检查 | `{ok:true}` |
| `/api/projects` | 项目列表 | `[{name,path,title,chapters,cards}]` |
| `/api/cards?project=P` | 素材卡概览 | `{project,types:[{type,label,file,count,items}],fields:{...}}` |
| `/api/chapters?project=P` | 章节列表 | `{project,chapters:[{file,title,updated_at}]}` |
| `/api/chapter?project=P&file=F` | 读单章正文 | 章节文本 |
| `/api/write/status?sid=S` | 写作会话状态 | `{status, ...}`（running/done/error/stopped） |
| `/api/template` | Markdown 设定模板 | `{template}` |

### POST
| 路径 | body | 返回 |
|------|------|------|
| `/api/projects` | `{path\|name, demo}` | `{path,name}` |
| `/api/cards` | `{project,type,card}` | `{id}`（按 id 覆写） |
| `/api/cards/delete` | `{project,type,id}` | `{ok:true}` |
| `/api/import-md` | `{project,md,use_llm,merge}` | `{stats,raw}` |
| `/api/write/start` | `{project,title,outline,character_ids?,...}` | `{sid}` |
| `/api/write/action` | `{sid,action,feedback?,text?}` | `{ok:true}` |
| `/api/write/stop` | `{sid}` | `{ok:true}` |

错误：4xx 带 `{"error":...}`；未捕获异常返回 500 并附带 `trace`（含堆栈），便于定位。

## 7. 前端要点

- `store.js`：全局响应式状态（`project`/`cardTypes`/`chapters`/`session` 等），所有接口调用集中在此。
- `api.js`：对上面 HTTP 接口的封装（注意字段名：列表卡片读 `d.types`、字段读 `d.fields`）。
- 写作看板：`api.writeStatus(sid)` 轮询，状态 `running` 时持续刷新、`done` 时停轮询并刷新章节。
- 人工审核面板：调 `api.writeAction(sid, action, ...)` 续跑 `human_review` 之后的图。
- 开发用 `npm run dev`（5173，已配 `/api` 代理到 8765）；生产用 `npm run build` 后由后端托管 `web/dist`。

## 8. 已知约束 / 待办

- 演示模式与项目模式共享同一套节点逻辑，区别仅在 `cards_dir` / `chapters_dir`。
- 卡片文件名 `wordviews.json`（worldview）拼写已固化，勿擅自改名以免读不到。
- 正文按 `chapter_001.txt` 顺序命名，依赖 `add_chapter` 的序号推断，勿手工重排导致跳号。
