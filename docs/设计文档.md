# StoryCaldron 设计文档

> 目的：让后续开发与维护人员在不通读全部源码的情况下，也能理解系统结构、数据流向与关键约定。
> 最后更新：2026-10-14（与拆分后的 `state`/`llm`/`prompts`/`nodes` 与 `common`/`sessions`/`api_*.py` 当前实现保持一致）。

## 1. 系统定位

StoryCaldron 是一个「多 Agent 协作小说创作」系统：用一张 LangGraph 工作流，把一章小说的
创作拆成「规划 → 写草稿 → 连续性检查 → 文风润色 → 人工审核 → 记忆更新 → 正典提案 → 落盘」
等节点，每个节点由大模型驱动，并支持在「人工审核」处暂停、由人介入修改或采纳。

整体分三层：

```
┌──────────────────────────────────────────────────────────────┐
│  前端（web/，Vue3 + Vite）  · 工作台 UI                       │
│  - 项目/素材卡/章节管理、写作看板、Agent 流式输出、人工审核面板 │
└───────────────┬──────────────────────────────────────────────┘
                │ HTTP / JSON  （BaseHTTPRequestHandler，单端口）
┌───────────────▼──────────────────────────────────────────────┐
│  后端服务（backend/web_server.py）  · 薄 HTTP 层              │
│  - 项目/卡片/章节 CRUD、Markdown 导入、写作会话控制、静态托管  │
└───────────────┬──────────────────────────────────────────────┘
                │ 直接调用
┌───────────────▼──────────────────────────────────────────────┐
│  核心逻辑（backend/collab_novel_agent.py + project.py）        │
│  - collab_novel_agent：LangGraph 工作流、LLM 调用、写作编排    │
│  - project：项目/卡片/章节 的本地文件存储（JSON + txt）       │
└──────────────────────────────────────────────────────────────┘
```

## 2. 目录与模块职责

| 路径 | 职责 |
|------|------|
| `backend/collab_novel_agent.py` | 创作核心（编排入口）：LangGraph 图编译、`FileCheckpointer` 检查点、`start_session`/`run_session`/`submit_human_action` 等对外 API、CLI 测试入口。 |
| `backend/state.py` | 状态/类型/常量/埋点：`CollabNovelState`、`ROLE_TEMPERATURES`、`track_step`、检查点落盘路径 `CHECKPOINT_FILE`。 |
| `backend/llm.py` | LLM 调用（`get_llm`/`_call_llm`）与素材卡 IO（`load_card_file`/`save_card_file`/`format_cards`）。 |
| `backend/prompts.py` | 各节点的提示词模板（`build_*_prompt`），节点只留「取状态→调 LLM→写回」。 |
| `backend/nodes.py` | 12 个节点函数 + 4 个路由（approve_card / continuity / human_review / approve_canon）。 |
| `backend/project.py` | 项目存储层：项目目录初始化、卡片读写、章节落盘、project.json 元信息。纯文件操作，不依赖 LLM。 |
| `backend/web_server.py` | HTTP 路由分发 + `main()` 启动 + 静态托管（已拆出 `common`/`sessions`/`api_projects`/`api_write`/`api_parse`）。 |
| `backend/common.py` | 共享路径常量（`HERE`/`ROOT`/`WEB_DIR`/`DIST_DIR`/`PROJECTS_ROOT`/`DEFAULT_PORT`）、`resolve_project_arg`、`config_of`。 |
| `backend/sessions.py` | `SESSIONS` 注册表、持久化与崩溃恢复续跑（注入写作驱动，避免与 `api_write` 循环依赖）。 |
| `backend/api_projects.py` | 项目/卡片/章节/大纲/模板/删除接口。 |
| `backend/api_write.py` | 写作驱动 `_drive`/`_start_thread` + `api_write_*` 四个接口（含 `ids_of`/`last_chapter_path`/`_snapshot`）。 |
| `backend/api_parse.py` | 拆书解析 `BOOK_TASKS` + `api_parse_*` 四个接口。 |
| `backend/data/` | 演示模式（无项目目录）下的全局素材卡与章节输出目录。 |
| `backend/output/` | 演示模式章节输出目录。 |
| `backend/projects/` | 多项目根目录，每个子目录是一个项目工作区。 |
| `backend/md_to_cards.py` | Markdown→卡片转换工具（命令行/导入接口复用），可接 LLM；支持六类卡（含去AI风）。 |
| `backend/book_to_cards.py` | 拆书解析：把整本小说 txt 按章节标记切分，逐章调 LLM 抽五类卡（人物/剧情/文风/伏笔/世界观，去AI风不由拆书提取），章节落盘 `chapters/`；复用 md_to_cards 的抽取工具。 |
| `web/src/` | 前端源码：`App.vue` 外壳、`store.js` 全局状态、`api.js` 接口封装、`components/*` 各面板。 |

## 3. 数据模型（项目工作区）

一个项目 = `<root>/` 目录，内部结构：

```
<root>/
  project.json            # 项目元信息：title、setting 摘要、chapters 章节索引
  cards/                  # 素材卡（每类一个 JSON 文件，键为 id）
    characters.json       # 人物卡
    stories.json          # 剧情卡（兼容旧名 plots.json）
    styles.json           # 文风卡
    foreshadowing.json    # 伏笔卡
    wordviews.json        # 世界观卡（文件名拼写如此，非 worlds）
    anti_ai.json          # 去AI风卡（作者手写 / 从 MD 导入；不由拆书解析自动抽取）
  chapters/               # 章节正文 chapter_001.txt ...（并按顺序命名）
  canon.md                # 正典/事实圣经：审批通过的正典提案按章节累积（#4）
  outline.md              # 全书大纲/结构圣经：整体结构走向 + 每章进展（#2）
```

**卡片类型约定**（`project.CARD_TYPES`）：

| type | 文件 | 中文标签 |
|------|------|----------|
| character | characters.json | 人物卡 |
| plot | stories.json（无则 plots.json） | 剧情卡 |
| style | styles.json | 文风卡 |
| foreshadowing | foreshadowing.json | 伏笔卡 |
| worldview | wordviews.json | 世界观卡 |
| anti_ai | anti_ai.json | 去AI风卡（写作/润色节点据此规避 AI 套路文风） |

- 卡片以 `id` 为主键，整文件按 id 覆写（`create_card` / `save_cards`）。
- `load_cards` 只在 `project/cards/` 内读取（**已修复**：不再回退到全局 `data/`）。
- 演示模式（前端不传 `project`）才用全局 `DATA_DIR` / `OUTPUT_DIR`。

## 4. 创作工作流（LangGraph）

图在 `collab_novel_agent.py` 末尾 `graph.compile(checkpointer=FileCheckpointer(),
interrupt_before=["human_review"])` 处构建（检查点为落盘版，重启可恢复）。节点与边：

```
START → load_context → plan_chapter → approve_card
approve_card --approved--> write_draft
approve_card --rejected--> plan_chapter        (带重试上限，超限强制通过)
write_draft → check_continuity
check_continuity --clean--> style_edit
check_continuity --issues_found--> fix_issues → check_continuity   (循环修正)
style_edit → human_review  ★interrupt_before 在此暂停
human_review --approved--> update_memory
human_review --revise--> style_edit           (回到润色，可多次)
update_memory → propose_canon → approve_canon
approve_canon --approved--> commit → END
approve_canon --rejected--> update_memory      (带重试上限，超限强制通过)
commit → 把 final_chapter 写入 <project>/chapters/ 并更新 project.json；同时把审批通过的正典提案追加到 `canon.md`、把本章进展追加到 `outline.md`
```

**关键设计点：**
- 状态对象 `CollabNovelState` 是单个大字典，贯穿所有节点（见 `start_session` 初始字段）。
- `track_step` 装饰器负责把每个节点的进展打印/记录到 `step_logs`，供前端「写作看板」轮询展示。
- `human_review` 节点本身不干活，真正暂停靠 `interrupt_before`，由前端 `api_write/action`
  提交 `approved` / `revise` / `edit` / `quit` 后再 `app.invoke` 续跑。
- `approve_card` 与 `approve_canon` 的「驳回→重做」有重试计数上限，避免无限循环（超过上限强制通过）。
- 去AI风卡（anti_ai）：`start_session` 装入 `anti_ai_cards`，由 `build_writer_prompt` / `build_style_edit_prompt` 注入写作与润色节点，约束生成文本规避 AI 套路文风（卡片为空则自动跳过）。

**跨章节与长期记忆（近期已落地 #1/#2/#4）：**
- 跨章节前情（#1）：`start_session` 在用户未填「上一章概括」时，自动用 `project.get_recent_chapter_excerpts` 从 `chapters/` 取最近 N 章正文**尾部**拼出前情，注入 `previous_summary`；并把近期章节片段存入 `prior_chapters`，供 `plan_chapter` / `write_draft` / `check_continuity` 节点参考，解决「写第 50 章看不到第 10 章」的问题。
- 全书大纲/结构圣经（#2）：`start_session` 加载 `<project>/outline.md` 到 `book_outline`，规划节点据此对齐整体走向；定稿后 `commit` 把本章进展（章节计划首行摘要）追加回 `outline.md`。
- 正典落盘（#4）：`propose_canon` 审批通过后，`commit` 把正典提案追加写入 `<project>/canon.md`，形成持续累积的「事实圣经」，作为后续章节的权威事实源。演示模式（无项目）落盘到 `OUTPUT_DIR/canon.md`、`OUTPUT_DIR/outline.md`。

**会话持久化与崩溃恢复（#8）：**
- 把 `graph.compile` 的内存级 `MemorySaver` 换成落盘版 `FileCheckpointer`（`collab_novel_agent.py`）：复用 `InMemorySaver` 的读写逻辑，仅在每次 `put`/`put_writes` 后把 `storage`/`writes`/`blobs` 整体 pickle 到 `<backend>/checkpoints.pkl`。LangGraph 的 thread_id 即会话 sid，故重启后按 sid 即可从最近一个检查点恢复、续跑。
- 会话元信息（项目、标题、状态、轮次、成稿路径）另落盘 `<backend>/sessions.json`（`web_server.py` 的 `_save_sessions`/`_load_sessions`）。`main()` 启动时 `_load_sessions` 重建历史会话；其中 `running` 状态（如服务崩溃）会自动重新起线程续跑。
- `api_write/status`、`api_write/action` 经 `_ensure_session` 兜底：即便内存 SESSIONS 被清空，也能从注册表或检查点恢复，不会误报「会话不存在」。

## 5. LLM 调用约定

- 唯一入口：`_call_llm(prompt, system, temperature)`，失败返回 `""` 供上层降级。
- 客户端工厂 `get_llm(temperature)` 按温度缓存 `ChatOpenAI` 实例，不同角色（规划/草稿/润色…）温度不同。
- 默认指向**本地 llama.cpp**：`http://localhost:8080/v1`，key=`dummy`（见 `DEFAULT_LLM_*`）。
- 可用环境变量覆盖：`LLM_MODEL` / `LLM_BASE_URL` / `LLM_API_KEY`。
- 因本地服务连接复用偶发 404，默认 `LLM_FORCE_CONNECTION_CLOSE=True`（每次新建连接）。

> 注意：当前默认不是 DeepSeek/云端，必须在 `localhost:8080` 起了兼容 OpenAI 的推理服务才能跑通写作；
> 接云端需设置上述环境变量（详见《开发指南》）。

## 拆书解析（book_to_cards）

把整本小说 txt 拆成「章节文件 + 五类素材卡」，**两段式**：先解析出预览方案（不写入），用户在前端预览/勾选后再提交写入。

1. `split_chapters(txt)`：识别「第N章 / Chapter N / 第N回」切成 `[(标题, 正文)]`；无标记则回退为单段（标题「全书」）。
2. `plan_book(txt)`：逐章 `extract_chapter(title, body)`（一次 LLM 调用返回五类卡 characters/plots/styles/foreshadowings/worldviews，模型不可用则只拆章不抽卡），跨章按 `id` 合并，**只返回方案、不落盘**。
3. `commit_book(project_dir, plan, chapter_idxs, card_ids, merge, clear_chapters)`：按勾选把章节写入 `chapters/`、把卡片写回 `cards/`；
   `clear_chapters=True` 时先 `proj.clear_chapters` 清空已有章节（对应「导入前清空已有章节」选项）；`merge` 控制卡片与已有合并/覆盖。

接口（轮询 + 两段式）：
- `POST /api/parse-book` 起后台线程跑 `plan_book`，返回 `{task_id}`；
- `GET /api/parse-book/status?task=` 轮询进度；`status=done` 时 `result` 带回预览方案 `{chapter_count, chapters:[{title,chars}], cards:{ctype:[card]}}`；
- `POST /api/parse-book/commit` 提交写入，body `{task, project, merge, clear_chapters, chapters:[下标], cards:{ctype:[id]}}`，返回统计；
- `POST /api/parse-book/stop` 中止解析。

## 6. 后端 HTTP 接口契约

基底：`http://127.0.0.1:8765`。所有接口 `application/json; charset=utf-8`。
`project` 参数传项目绝对路径；省略则走演示模式（`projects/default` 或全局 `data/`）。

### GET
| 路径 | 说明 | 返回 |
|------|------|------|
| `/api/health` | 健康检查 | `{ok:true}` |
| `/api/projects` | 项目列表 | `[{name,path,title,chapters,cards}]` |
| `/api/cards?project=P` | 素材卡概览 | `{project,types:[{type,label,file,count,items}],fields:{...}}` |
| `/api/chapters?project=P` | 章节列表 | `{project,chapters:[{file,title,updated_at}]}` |
| `/api/chapter?project=P&file=F` | 读单章正文 | 章节文本 |
| `/api/outline?project=P` | 读全书大纲/结构圣经 | `{project, outline}` |
| `/api/write/status?sid=S` | 写作会话状态 | `{status, ...}`（running/done/error/stopped） |
| `/api/parse-book/status?task=T` | 拆书任务进度 | `{status, progress:{done,total}, logs, stats, error}` |
| `/api/template` | Markdown 设定模板 | `{template}` |

### POST
| 路径 | body | 返回 |
|------|------|------|
| `/api/projects` | `{path\|name, demo}` | `{path,name}` |
| `/api/cards` | `{project,type,card}` | `{id}`（按 id 覆写） |
| `/api/cards/delete` | `{project,type,id}` | `{ok:true}` |
| `/api/import-md` | `{project,md,use_llm,merge}` | `{stats,raw}` |
| `/api/write/start` | `{project,title,outline,prev?,characters?,plots?,styles?,fore?,worlds?,anti_ai?}` | `{sid}` |
| `/api/write/action` | `{sid,action,feedback?,text?}` | `{ok:true}` |
| `/api/write/stop` | `{sid}` | `{ok:true}` |
| `/api/parse-book` | `{project, name, text, merge}` | `{task_id}`（后台线程跑 plan_book，轮询上面 status） |
| `/api/parse-book/commit` | `{task, project, merge, clear_chapters, chapters:[下标], cards:{ctype:[id]}}` | `{stats}`（按勾选写入） |
| `/api/parse-book/stop` | `{task}` | `{ok:true}` |
| `/api/outline/save` | `{project, outline}` | `{ok:true, path}`（整体覆盖保存 outline.md） |

错误：4xx 带 `{"error":...}`；未捕获异常返回 500 并附带 `trace`（含堆栈），便于定位。

## 7. 前端要点

- `store.js`：全局响应式状态（`project`/`cardTypes`/`chapters`/`session` 等），所有接口调用集中在此。
- `api.js`：对上面 HTTP 接口的封装（注意字段名：列表卡片读 `d.types`、字段读 `d.fields`）。
- 写作看板：`api.writeStatus(sid)` 轮询，状态 `running` 时持续刷新、`done` 时停轮询并刷新章节。
- 人工审核面板：调 `api.writeAction(sid, action, ...)` 续跑 `human_review` 之后的图。
- **素材卡编辑（`CardsDrawer.vue`）**：表单只渲染 `CARD_FIELDS` 中除 `id` 外的字段——新建卡不暴露 id，落库时由 `api_save_card` 自动分配（`<类型前缀>_<随机>`）；编辑已有卡时 id 只在标题旁只读展示，保证主键不可被误改。
- **创作输入（`Composer.vue`）**：高级选项里的「指定卡片」按 `store.cardTypes` 分组渲染复选框（`PARAM_OF` 把卡片类型映射到 `/api/write/start` 的 body key），点选即用、支持整组全选/清空；某类一张都不勾则以空串提交，后端按「该类全部卡片」处理。切换项目时清空已勾选，避免串项目 id。
- 开发用 `npm run dev`（5173，已配 `/api` 代理到 8765）；生产用 `npm run build` 后由后端托管 `web/dist`。
